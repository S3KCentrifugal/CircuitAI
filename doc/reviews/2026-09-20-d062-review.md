# Review of D-060 / D-062 - TECH economy and layout rebuild (2026-09-20)

Reviewed: the change set the owner described (Supreme opener, three-resource
model, storage, converters, progressive nano rows, compact placement,
recycling, TECH-only activation), as it stands in the working tree at 21:41.
Method: read of the native and script code paths, the decision entries, the
map profile, the test harness; state checks of the deployed DLL and script.
No code was changed by this review.

**Verdict.** Sound design, consistent implementation, one high-severity
hole in the opener's factory hold, a handful of medium items. Deployable for
a played test now; the hole should be closed before the second game.

## Verified

- The installed DLL (`69ec41f0…`) is the build named in the report, built
  from a separate Recoil checkout (`bar-RecoilEngine-s3k-build`, origin the
  read-only tree), so the read-only rule holds. The installed script and
  config trees match the working tree file for file.
- Every fix of the earlier review (D-059) is still present: the reclaim ids,
  the explicit reserved search, the friendly exclusion, the ferry dump and
  park, the energy-limit copy, the wave abort, the merge clock, `CanBuild`
  on the planner, the role-switch state snapshot (extended to the three new
  economy flags). CR-015 is moot: the bands it patched no longer exist.
- The eco planner defers `advconv` and `afus` to the module when one stands
  (`EcoPlanner::Execute`), so there is one authority for those two defs.
  Fusions, solars and winds stay the planner's, by design (temporary energy
  around the cluster, recycled later).
- Storage: the opener builds one energy storage after the lab, native
  automatic storage is off, the planner's cap is also one, queued tasks
  count. Consistent.
- Converters read the def's real consumption (`GetEnergyUse`) and require a
  90 % bank, measured surplus at least the consumption, no stall, no
  generator under construction. Four per AFUS, a fifth from surplus.
- Module ordering: nanos to the desired row count, then one AFUS, then
  converters to the goal, then the next AFUS; one AFUS frame at a time; two
  nanos and two converters in flight at most. Slots are claimed natively
  (`PinLayoutTask`), a failed pin aborts the task (`pinFailed`), a cancelled
  task unclaims. Reachability filters slot choice per builder.
- Save/load: `Adopt` runs from `Layout::Update` when native state exists
  and the script has none; claims are serialized. KI-406 closed with reason.
- The activation model changed and is documented: `behaviour.json`
  `layout.enabled` is now `true` in the experimental profiles ("JSON
  permits") and only TECH opts in from script. Other roles never call the
  layout API, so their placement is unchanged; the guarantee is now a script
  one, not a JSON one.

## Findings

### R-1 (high) - The opener can hold the start factory for ever

`Opening::Init` sets `holdStartFactory` when no T1 lab stands. Only the
commander's `Opening::MakeTask` releases it, and only after the mex and wind
phases complete. There is no time cap and no other release. Three ways to
never release it:

- the commander dies during the opening (`MakeTask` runs for the commander
  only, `complete` stays false);
- `claimed < target` but `EnqueueMexWithin` returns null (every reachable
  spot open but none `CanBeBuiltAt` for the mex def): the commander gets
  `Wait(1 s)` for ever;
- winds wanted but `EnqueueT1Wind` returns null (def unavailable or
  capped): the same wait loop.

Effect: no factory, ever; the AI is dead on the field. Suggested: a hold
deadline (`OpeningMaxSeconds`, 120 or so) after which `complete` is forced
and the hold dropped, plus a release on commander death and on any wait
loop that repeats more than N times.

### R-2 (medium) - The home-cluster count treats any claimed spot as ours

`GetClaimedMexCountWithin` counts a spot as claimed when it is not open,
whoever holds it. An ally's or an enemy's extractor inside the 1,200-elmo
home radius advances the opener as if TECH had built it, so TECH opens with
fewer of its own mexes on shared or contested starts. Suggested: count only
spots whose extractor is on our team (the metal manager knows the owner), or
count TECH's own mex tasks and units within the radius.

### R-3 (medium) - The first AFUS starts without the energy focus rules

`Stage` returns 2 (AFUS) as soon as the module's nanos reach the desired
count and income clears +70 metal / +2000 energy. Converters check
`GetEnergyUnderConstruction()`; the AFUS branch does not, and
`MakeModuleTask` runs before `Tech_RedirectEnergyToReactor` in the ladder.
A fusion under construction elsewhere gets a parallel 9,700-metal frame.
Suggested: the same `GetEnergyUnderConstruction()` guard on stage 2, or run
the redirect before the module task.

### R-4 (medium) - Regional build power counts transients

`GetBuildPowerNear` sums every assist-capable unit within 700 elmos of the
module centre, including the commander and any constructor passing
through. A row can be added because four T1 constructors happened to be
near, then those leave. The 2.5 BP per metal target is sound; the sample
should be turrets plus constructors that are actually assigned to the
module, or a rolling minimum.

### R-5 (low) - Threat-aware reachability shrinks the opener's target silently

Both the target and the claimed count use `CanReachAtSafe`, so a home spot
under early threat drops out of both and the opener moves on with two mexes
and no log line saying why. A level-1 line when the reachable target is
below the cap would make the first played game readable.

### R-6 (low) - Ordering in the builder ladder

`MakeFactoryNanoTask` and `MakeModuleTask` run before the tier split, the
float-spend rule and the reactor redirect. They run after the mex and geo
default gate, which is right. The commander is protected by `CanBuild`. Worth
a comment at the call site so the next change does not move them.

### R-7 (low) - Tests not re-run here

`tests/base_layout_geometry_test.cpp` is a 200-line `Check` harness over
the geometry header. The `build-layout-tests/` directory was removed while
this review ran, so the pass was not reproduced; accepted on the report.
A `tests/README` line with the configure and run commands would let anyone
reproduce it.

## Recommendation

Close R-1 before the second played game; it is a few lines (a deadline and
a commander-death release). R-2 and R-3 are the next two. The rest are
polish. The first played game should watch the level-1 `[TECH][Opening]`
lines and the `RESERVE:` claim lines against KI-408's checklist.
